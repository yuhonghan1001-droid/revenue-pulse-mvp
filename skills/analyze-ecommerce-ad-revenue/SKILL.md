# 电商广告收入 BP 分析

把分散的广告经营数据和财务数据转化为可以支持决策的 BP 分析。把每一项结论都当作需要治理的“主张”，保留指标定义、数据截止时间、来源证据、不确定性和下一步责任人。

## 按需读取参考资料

- 计算或比较收入前，必须读取 [指标口径](references/metric-contracts.md)。
- 拼接两个及以上数据源、检查数据健康度或判断是否可以发布结论时，读取 [数据质量与分析护栏](references/data-quality-and-guardrails.md)。
- 解释差异、更新预测或诊断预警时，读取 [收入动因分析](references/driver-analysis.md)。
- 生成看板解读、管理简报、飞书消息、邮件或行动清单时，读取 [管理层简报标准](references/management-brief-standard.md)。
- 修改本 Skill、吸收业务反馈或宣称能力升级时，读取 [评测与迭代机制](references/evaluation-and-iteration.md)。

## 建立分析约定

开始计算前：

1. 明确决策问题、阅读对象、数据截止时间、报告周期和金额单位。
2. 明确比较基准：去年可比期间、按时间进度拆分的预算、上一版预测和最新预测。
3. 列出全部数据源，并记录负责人、数据粒度、主键或复合主键、关联键、更新时效和数据覆盖区间。
4. 区分经营流水收入、计费确认收入、财务确收收入、返点、退款和净收入，禁止混用。
5. 把缺少的数据记录为“已知缺口”，禁止静默填零。

如果需求存在歧义，采用最不容易误导管理决策的解释，明确标注假设并继续；只有当不同选择会实质改变决策时，才停下来要求确认。

## 执行分析流程

### 1. 建立受治理的数据集

关联数据前，统一日期、币种、金额单位、正负号、ID 和分类值。

每次关联前都验证数据粒度。若关联导致事实表行数异常增长，立即停止并查明原因。保留数据源 ID、行级证据或聚合证据，供后续结论追溯。

在本项目中运行：

```bash
python3 data_pipeline/run_pipeline.py
```

把 `data_pipeline/config/source_registry.json` 作为数据源约定。由模拟 CSV 切换到真实系统时，只替换数据读取方式，不随意修改稳定的数据源 ID。

### 2. 执行数据质量门槛

检查数据及时性、完整性、主键唯一性、关联成功率和财务对账情况，并将结果分为：

- `pass`：可以正常发布。
- `warn`：可以发布，但必须明显展示限制和置信度。
- `fail`：停止自动生成管理结论；只报告阻断数据源、责任人和修复要求。

禁止用流畅、确定的文字掩盖未通过的数据质量检查。

### 3. 计算统一指标

根据需求计算累计净收入、可比同比、时间进度预算达成率、最新月末预测、预测较预算差异、返点率和商家预算利用率。

每个管理指标必须保留：

- 指标定义和公式；
- 数据截止时间和计算粒度；
- 来源数据源 ID；
- 对账状态；
- 指标负责人。

### 4. 先比较，再解释

按照四层 BP 框架判断：

1. 实际：截至当前已经发生了什么？
2. 同期：与去年真正可比的期间相比如何？
3. 预算：考虑时间进度后是否在轨？
4. 预测：月底预计达到多少？与上一版预测相比发生了什么变化？

区分“不利差异”和“不利经营结果”。策略、流量分配或返点政策变化可能使收入下降符合预期。

### 5. 拆解收入动因

使用 [收入动因分析](references/driver-analysis.md) 中的三棵动因树：

- 流量变现；
- 商家需求；
- 计费到确收。

分别排序正向和负向贡献，先量化贡献，再描述原因。把策略事件、促销和日历错位作为业务背景或待验证假设，不直接视为因果证据。

### 6. 建立可追溯结论

把重要陈述分成：

- `fact`：由数据直接计算或观察到的事实；
- `forecast`：基于明确假设产生的未来预测；
- `judgment`：由证据支持的 BP 判断；
- `risk`：尚未确认的风险或数据限制。

为每项陈述附上证据引用、置信度和来源数据源 ID。无法证明因果关系时，使用“与……相关”“与……一致”或“需要业务确认”，不要使用确定性因果表述。

### 7. 生成管理输出

按照管理意义组织内容：

1. 核心结论；
2. 实际相对同期、预算和预测的表现；
3. 最重要的正向和负向动因；
4. 数据置信度和已知缺口；
5. 行动、责任人、截止时间和触发条件。

可以根据阅读对象调整详略，但不能改变指标定义。财务版本必须可审计，业务版本必须可行动。

## 发布前校验

如果已经生成结构化简报，运行：

```bash
python3 skills/analyze-ecommerce-ad-revenue/scripts/validate_brief.py path/to/brief.json
```

把校验错误视为发布阻断项，逐条确认警告。当代码或看板数据发生变化时，同时运行项目数据管道和产品测试。

## 迭代 Skill

把具有普遍性的业务反馈转化为受控的 Skill 变更：

1. 保存被质疑或失败的案例，并删除个人信息与商业敏感信息。
2. 判断根因属于数据、指标口径、分析顺序、动因逻辑、表达方式还是业务背景缺失。
3. 把修正抽象为范围最小、可以复用的规则。
4. 新增或更新评测案例。
5. 同时运行新案例和全部历史回归案例。
6. 将 Skill、参考规则和评测变更放在同一次提交中。

不能因为修改了提示词就宣称 Skill 变强。只有新增案例通过、历史案例不回退时，才能视为能力升级。

## 保留人的责任

涉及目标调整、计提、收入确认、商家激励或资源分配等高影响结论时，必须经过财务 BP 审核后再分发。AI 只提供分析支持；指标责任和业务决策必须落实到明确的人。

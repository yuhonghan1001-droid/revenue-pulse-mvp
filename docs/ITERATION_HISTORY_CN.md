这个项目不是一次做完的。

## 4. 第 1 轮：建立收入分析 MVP

### 出现的问题

- 财务 BP 需要从二十多个来源下载、拼接和核对数据；
- 人工流程每月只能完成一到两次；
- 同比、预算、预测、动因和数据质量分散在不同表格；
- 没有一个可重复运行、可展示的产品原型。

### 改动了什么

- 建立 24 个模拟数据源；
- 建立数据源注册表；
- 建立 Python 数据管道；
- 生成统一 `dashboard.json`；
- 建立 Next.js 分析看板；
- 加入累计收入、同比、预算、预测和动因；
- 加入数据健康、指标口径和证据链展示；
- 加入基础 D1、Worker 和 Sites 结构；
- 加入页面回归测试。

### 怎么改动的

```text
24 个模拟 CSV
→ 数据源注册表
→ Python 拼接与校验
→ 指标和预测
→ dashboard.json
→ Next.js 看板
```

数据管道统一商家、行业、区域、产品、流量和日期等维度，并检查重复键、完整性、关联成功率和财务对账。

### 改动规模

- 提交：`b0431e8`
- 57 个文件；
- 约 153,152 行新增；
- 大部分行数来自模拟数据和 `pnpm-lock.yaml`。

### 达到的效果

- 得到第一版可运行收入分析 MVP；
- 能演示约 27,408 条收入事实记录的拼接；
- 能展示收入、同比、预算、预测、动因和数据质量；
- 建立了后续 Skill、自动化和飞书能力的技术底座。

### 遗留问题

- 全部数据仍是模拟数据；
- 业务口径默认每天都有“收入”；
- 看板和快照仍有静态假设；
- 尚未形成完整的自动运行和推送闭环。

## 6. 第 3 轮：升级为 BP 收入分析闭环

### 出现的问题

初版仍存在多项产品和工程缺口：

- 日期、标题和管理文案存在静态内容；
- 页面不同区域可能读取不同时间点的数据；
- 没有可复用、可评测的财务 BP Skill；
- 没有稳定保存每次分析版本；
- 没有每日自动运行；
- 没有飞书个人私信；
- 缺少规则引擎和 AI 语言层的明确边界。

### 改动了什么

- 增加动态截止日期、月份、进度和文案；
- 扩展 Python 管道的预测、动因、质量和证据逻辑；
- 增加 `analyze-ecommerce-ad-revenue` Skill；
- 增加指标合同、质量护栏、动因分析和简报标准；
- 增加 Skill 输出校验脚本；
- 增加 D1 `analysis_runs`；
- 增加 `/api/analysis/run` 和 `/api/analysis/latest`；
- 统一整个看板读取同一份最新完整快照；
- 增加 GitHub Actions 每日任务；
- 增加飞书个人私信和群机器人备用方式；
- 增加规则引擎与可选 OpenAI 语言增强；
- 增加更完整的测试和类型定义。

### 怎么改动的

```text
数据管道
→ 完整 dashboard 快照
→ Worker 执行 Revenue Skill
→ D1 保存输入和结果版本
→ 整个看板读取最新快照
→ 飞书推送
```

数字、质量状态和证据由程序生成；AI 只能优化语言，不能修改受治理指标。没有 OpenAI Key 时自动使用规则模板。

### 改动规模

- 提交：`9ff24c2`
- PR：#1；
- 30 个文件；
- 4,823 行新增、182 行删除。

### 达到的效果

- 形成从数据管道到看板、Skill、D1 和飞书的完整链路；
- GitHub Actions 可按北京时间 09:45 计划运行；
- 飞书个人私信经过真实测试；
- 看板不再混用静态快照和实时 Skill 局部结果；
- 分析结果可追溯到 Skill、输入、时间和引擎版本。

### 已知限制

- 24 个源仍然是模拟数据；
- 计划任务重算的是仓库内数据，源文件不更新时业务数字也不会更新；
- 当前收入模型仍预设日常存在收入数据；
- 旧版可以在分析请求中直接自动推送，没有人工审核环节。

## 7. 第 4 轮：修复计划任务请求被拒绝

### 出现的问题

GitHub Actions 从云端调用线上 `/api/analysis/run` 时，请求被托管安全层识别为不明确的自动流量，导致计划任务无法稳定发布快照和发送飞书。

### 改动了什么

只修改 `data_pipeline/publish_snapshot.py`：

- 增加 `Accept: application/json`；
- 增加专用 `User-Agent`：

```text
RevenuePulse-GitHubActions/1.0
```

### 怎么改动的

没有降低接口令牌校验，也没有关闭安全层，而是让合法计划任务带上可识别的客户端身份。

### 改动规模

- 提交：`830bc9a`
- PR：#3；
- 1 个文件；
- 5 行新增。

### 达到的效果

- GitHub Actions 请求可以被正确识别；
- 自动任务完成数据生成、线上分析、版本保存和飞书推送；
- 已成功运行的记录为 Actions Run `30158255701`。

### 重要说明

这次只解决“请求是否能成功到达”的问题，没有解决“计划时间和实际推送时间是否一致”的问题。

当前工作流只记录 GitHub 自身的运行时间，没有在产品数据中分别保存：

- `scheduled_at`；
- `started_at`；
- `analysis_finished_at`；
- `feishu_sent_at`。

因此，用户看到“09:45 计划运行、17:00 才收到消息”时，仅凭现有产品记录不能准确判断延迟发生在 GitHub 调度、任务排队、分析执行还是飞书发送。这个问题已经进入 v0.2 Issue #18。

## 9. 第 6 轮：从“每日收入”调整为“数据盘点 + Sales-only”

### 出现的问题

在重新讨论真实业务流程时，暴露出原产品最关键的口径问题：

1. 财务 BP 日常更可能拿到 GMV、广告签单、广告消耗或可计费金额；
2. 月结实际收入通常在月底关账后才能得到，不是每天都有；
3. 用户目前也不能确定实际会拿到哪些字段和文件；
4. 原产品把每日经营数据直接放进“收入”框架，存在误导风险；
5. 缺少预算、去年同期或历史数据时，不应补零或强行预测；
6. 旧版 GitHub Actions 会自动推送，缺少人工审核；
7. 09:45 与实际收消息时间的差异暴露出时间审计不足；
8. 真实文件可能包含敏感数据，不能默认上传和长期保存。

### 改动了什么

这轮没有直接改业务代码，而是先完成规范化重设计：

- 新 PRD：首期只做数据盘点和 Sales-only；
- 新 UI/UX：导入、映射、质量、看板、证据、审核、推送；
- 新技术方案：浏览器内解析原始文件，D1 只存聚合和审计；
- 新 MVP 开发计划：M0–M5 六阶段；
- 新 GitHub Kanban；
- 15 个可独立验收的 Issues；
- 新 Sales Skill 与旧 Revenue Skill 并行的方案；
- 飞书从自动推送改为目标状态“人工审核后推送”。

### 怎么改动的

产品逻辑改为：

```text
上传 CSV / XLSX
→ 浏览器内字段画像
→ 用户确认 Sales 定义
→ 数据质量检查
→ 判断哪些指标可用
→ 规则引擎计算 Sales
→ AI 只整理文字
→ 用户审核
→ 人工确认后发飞书
```

关键口径改为：

```text
Sales 实际 ≠ 收入暂估 ≠ 收入预测 ≠ 月结实际收入
```

### 改动规模

已完成但尚未提交：

- 1 份批准 PRD；
- 1 份批准 UI/UX 规范；
- 1 份批准技术方案；
- 1 份批准 MVP 开发计划；
- 1 个 GitHub Project；
- 15 个 GitHub Issues（#5–#19）。

当前原仓库 Git 状态为 `?? docs/`，说明 v0.2 文档尚未提交。

### 达到的效果

- 从错误的“默认每日有收入”调整为“先识别手里有什么数据”；
- 首期不再生成收入暂估或月结实际收入；
- 用户必须确认 Sales 的业务含义；
- 缺数据时明确显示不可用，不自动填零；
- 数据质量失败时不生成确定性结论；
- 原始文件计划只在浏览器内解析；
- 飞书目标流程增加人工审核、digest 和幂等保护；
- 开发任务已经按依赖拆分，可逐个验收。

### 当前状态

这轮仍然是“批准后的设计和计划”，不是已上线功能：

- 旧版公开看板仍是收入演示看板；
- 旧版 GitHub Actions 仍执行 `publish_snapshot.py --push`；
- 旧版仍可能自动发送飞书；
- 新的 CSV/XLSX 上传尚未开发；
- 新 Sales Skill 尚未开发；
- 人工审核推送尚未开发；
- 第一个开发 Issue #5 尚未认领。

## 11. 为什么这次不直接继续写代码

因为这次发现的不是一个页面小问题，而是产品输入和财务口径需要调整：

```text
原假设：每天能拿到收入
真实情况：日常更可能只有 Sales，收入月底才确认
```

如果不先修正 PRD、UI、技术合同和验收条件，继续在旧架构上写代码，会把错误口径自动化并通过飞书放大。

因此，本次先完成需求对齐和任务拆分，再逐个 Issue 开发。这样可以保证每个阶段都能回答：

- 当前分析的是 Sales 还是收入；
- 数据是否足够；
- 数字从哪里来；
- 哪些结论是事实、预测或判断；
- 什么时候必须人工确认。
